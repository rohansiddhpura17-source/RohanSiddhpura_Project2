Space Weather Update Centre

When a trusted source changes, this page should tell you first, show you the evidence, and wait for your permission. It does not rewrite your project on its own.

Permission gate — how this works:
  1. Monitor (a separate script, monitor.py) checks sources and writes updates.json. It never edits the dashboard, simulator or presentation.
  2. Review (this page) lists what changed, the source link, and which sections would be affected.
  3. Approve or Reject here. Approve only creates an approved change pack below — the exact text to apply in the next step. Reject archives the item with a reason.
  4. Only after you approve does anything change in the project, and only the sections listed in the pack.

Why a separate script? A standalone HTML file sitting unopened on your SSD cannot monitor the web, and a file opened from file:// cannot reliably fetch live APIs because of browser CORS rules. The monitor must run separately — on your Mac, or as a scheduled GitHub Actions job — and this page reads its output.

2 — Two different channels (do not mix them up)

A. Live event data — can refresh automatically, with a timestamp

Current flares, CMEs, geomagnetic storms and Kp index. These are events, not explanations.

  • NASA DONKI: api.nasa.gov/DONKI/FLR, /CME, /GST — free api.nasa.gov key required; DEMO_KEY is rate-limited. Verify the current DONKI endpoint before production use.
  • NOAA SWPC JSON (no key): planetary Kp, G/S/R scales, alerts — services.swpc.noaa.gov. SWPC JSON formats have changed before, so pin a snapshot and treat a schema change as “needs review”, not as data.

Safe auto-update rule: refresh only the event list, chart values, timestamps and source links, and always show “Last updated: … • Source: …”. Never let a live feed rewrite a quiz answer, an explanation or the simulator's physics.

B. Scientific knowledge — verify before publishing, always

New documents, revised pages or changed statements from the eight sources. These go through the approval queue in section 3. No auto-publish, even if an AI draft looks good.

4 — What happens after you approve?

  1. The item moves to Approved with a timestamp, and the change pack above shows the exact source, affected sections and proposed text.
  2. In the next step (with you, or with me in a new session), that pack is applied to the named files only, the files are diff-checked, and a new ZIP is built — the same verification pattern used for the viewport buttons.
  3. Rejected items stay archived with their reason, so the same change is not silently re-proposed as new.

If you want a real backend later: a weekly GitHub Actions job running monitor.py, committing only updates.json when it changes, and opening an issue / notification for you to review. It should never commit edits to the three apps by itself. That job needs a repository and a decision about where the apps live (GitHub vs. your SSD) — that is the next choice, not something to set up silently now.
